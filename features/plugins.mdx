## Überblick

Die Mobile-App (PWA + Android) besteht aus einem schlanken Kern (Stream, Detail-Card, Compose, Suche) und **Capabilities** — first-party Plugins, die der Nutzer im Plugin-Katalog an- und abschalten kann. Jede Capability deklariert ihre **Grants** (`content:write`, `net:fetch`, `ai`, …) und ihre Beiträge sichtbar auf der Plugin-Karte.

<Callout kind="info">

**Zwei Kataloge, nicht vermischen:** Katalog **A** = Compose-Eingabe (Felder wie `segmented`, `stepper`, `tokens`, `place`), Katalog **B** = render_ui-Anzeige (`Markdown`, `SectionHeader`, `ChipRow`, `StatBar`, `Heatmap`, …) — eine Zod-Quelle im `ui-contract`, drei Surfaces (live · Editor · PDF).

</Callout>

## Was eine Capability beisteuern kann

| Beitrag | Beschreibung |
| --- | --- |
| **Aktionen** | Kontextbezogene Einträge im Aktionen-Menü (`surface: 'bar'` = Pill oben, `'section'` = AKTIONEN-Grid), gefiltert per `appliesWhen(target)` |
| **Glance-Chips** | Proaktive Chips auf der Home (fällige Routine, Wetter am gespeicherten Ort) |
| **Omnibar-Intents** | Texteingaben wie „reise nach Lissabon" oder „menüplan" öffnen direkt den passenden Wizard |
| **Detail-Sections** | Abschnitte auf jeder Detail-Card (`registerDetailSection`): Rang, Badge, einklappbar, gefiltert nach `contentTypes` |
| **Detail-Themes** | CSS-Scope + `enhance(host, ctx)` für typ-spezifische Aufwertung (Karte im Orts-Detail, Zutaten-Thumbnails im Rezept) |
| **Composer** | `detail.compose` ersetzt die komplette Detail-Komposition eines Content-Types durch Katalog-B-Nodes |
| **Skills** | Deklarative LLM-Wizards — siehe [Skills](/features/skills) |

## Erweiterungspunkte der Detail-Card

Vier Ebenen, von grob nach fein:

1. **`detail.compose`** — ersetzt die gesamte Komposition (z. B. Reise-Dokument: StatBar + Tages-Abschnitte + Packliste). Muss den Body-Fallback selbst durchreichen.
2. **`detailThemes`** — dekoriert das Gerenderte (Scope-Klasse + `enhance`), z. B. Karten-Block und Wetter im Orts-Detail.
3. **`registerDetailSection`** — hängt Abschnitte an (Wissen, Routine-Heatmap, Nexus-Vorschau); Plugin-Gate gehört **in** die `render`-Funktion.
4. **Aktionen** — Top-2 nach Rang als Pills, Rest im „…"-Overflow und im AKTIONEN-Grid.

<Callout kind="warning">

**Lexical ist Kanon.** `data.root` (lexical/v1) ist das Schreibformat; EditorJS-Blöcke (`data.blocks`) sind Alt-Bestand — nur lesen/migrieren, nie neu schreiben. Struktur (Checklisten-Items, Felder) lebt in `structured_data.fields`, nicht im Body.

</Callout>

## Das konsolidierte deklarative System (Juli 2026)

Deklarative Plugins sind **reine Daten** (JSON-Manifeste, kein Code) — und laufen seit der Konsolidierung über genau eine Pipeline für **alle** Hosts:

<Steps>

1. **Eine Manifest-Quelle.** Die Erst-Partei-Manifeste leben in `assistant-kit apps/mobile/src/plugins/first-party-manifests.ts` (bewusst import-frei). Der Generator `export-plugin-manifests.mjs` erzeugt daraus `server/first-party-plugins.json` — Mobile-App und Server werten also identische Manifeste aus.

2. **Eine Aktivierung.** Per User auf dem Server: `GET/PUT /api/plugins/enabled` (Katalog: `GET /api/plugins/catalog`). Die Mobile-App synct beim Boot (Union mit lokalen Seeds) und pusht jedes Toggle; der Desktop-Plugin-Store togglet direkt.

3. **Quick-Actions server-injiziert.** `GET /api/assets/quick-actions/:type/:id` hängt die passenden Plugin-Aktionen an (`action: "plugin-effect"` + Effekt-Payload, DeclWhen-Matching gegen contentType/tags/Felder). Extension und Desktop rendern sie ohne eigenen Plugin-Runtime.

4. **Hooks server-materialisiert.** Trigger (`interval`, `cron`, `contentChange`, `webhook`) werden bei jedem `PUT /enabled` direkt aus Manifest × Aktivierung in die Trigger-Registry geschrieben — ein Toggle wirkt sofort, egal von welchem Host. Der Mobile-Push veredelt anschließend `fromSetting`-Referenzen mit den echten Nutzer-Settings.

5. **Ein Effekt-Dispatcher.** `runDeclEffect` (im geteilten `brainz-detail-host`-Bundle) führt `setStatus`, `setContentStatus`, `createEntry`, `notify`, `openUrl`, `copy` über die bestehenden REST-Routen aus — Extension und Desktop teilen sich die Implementierung; die Mobile-App behält ihren tief integrierten ActionHost-Runner.

</Steps>

<Callout kind="info">

**Trust-Gates:** Aktionen und Trigger greifen nur für `trust: first | verified` mit passender Permission (`triggers:schedule` etc.); `community` bleibt außen vor. Theme-Tokens sind auf die `--bz-*`/`--bzc-*`-Namespaces begrenzt.

</Callout>

### Legacy: das imperative Bundle-System

Das ältere Code-Bundle-System (Client-SDK `core.plugin-{registry,api,sandbox}.js`, Server-VM `plugin-runtime.js`, Marketplace `/api/registry/plugins`) ist **dokumentiertes Legacy ohne reale Plugins** — deutlich gebannert, bewusst nicht gelöscht. Im Desktop-Plugin-Store sind seine Tabs als „(Legacy)" markiert. Nicht verwechseln: die **aktiven** Pulse-Plugins laufen über den separaten `pulse-plugin-runtime` und sind kein Teil davon.

## Konventionen

- **Design-Tokens:** `--bz-*` (Anzeige) / `--bzc-*` (Compose); Sheets sind self-theming (Light-Tokens + `--dark`-Override via `matchMedia`). Icons über den bzIcon-Service — keine Emojis.
- **Bundle-Splitting:** Sheets laden per dynamischem `import()` am Aktions-Einstieg; geteilte Konstanten leben in kleinen Modulen, damit Lazy-Chunks nicht ins Haupt-Bundle rutschen.
- **Stream ist event-sourced:** Neues entsteht über `contentRepo.create` (emittiert `entity.created`) oder den generischen `POST /api/content` — dann erscheint die Karte von allein im Stream.
