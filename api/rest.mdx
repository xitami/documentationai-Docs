## Überblick

Die Brainz REST API umfasst 533 Endpunkte in 79 fachlichen Gruppen. Die Dokumentation entsteht code-first direkt aus den Server-Routen und bleibt dadurch mit der laufenden Implementierung synchron.

Unter der Haube erzeugt ein eigenes OpenAPI-Registry-System aus Zod-Schemas eine OpenAPI-3.1-Spezifikation zur Laufzeit. Routen dokumentieren sich selbst über ein gemeinsames `registerRoute()`-Muster, das Methode, Pfad, Tags, Request-Schema und Response-Schema an einer Stelle beschreibt.

## Live-Dokumentation

Zwei Endpunkte stellen die REST-Dokumentation direkt bereit: eine maschinenlesbare Spezifikation und eine interaktive UI für die manuelle Exploration. Beide Quellen werden aus denselben Route-Definitionen erzeugt.

<Callout kind="tip">

`/api/docs` ist der schnellste Einstieg, wenn du die gesamte API interaktiv durchsuchen, Requests ausprobieren und Beispielaufrufe direkt vergleichen willst.

</Callout>

<ParamField path="/api/openapi.json" param-type="GET" required="true" show-location="false">
Maschinenlesbare OpenAPI-3.1-Spezifikation der kompletten REST API. Verwende diesen Endpunkt für Code-Generatoren, Validierung, Client-SDK-Workflows oder externe API-Tools.
</ParamField>

<ParamField path="/api/docs" param-type="GET" required="true" show-location="false">
Interaktive API-Referenz auf Basis von Scalar. Die Oberfläche zeigt Endpunkte, Parameter, Schemas und Beispielaufrufe und unterstützt Try-it-out direkt im Browser.
</ParamField>

Die folgenden Beispiele rufen beide Dokumentationsendpunkte direkt per `curl` ab.

<CodeGroup tabs="OpenAPI JSON,Scalar UI">

```bash
curl -i https://brainz.ai/api/openapi.json
```

```bash
curl -i https://brainz.ai/api/docs
```

</CodeGroup>

## Authentifizierung

Die REST API verwendet dieselbe Authentifizierung wie die GraphQL API: geschützte Endpunkte erwarten ein Bearer-JWT im `Authorization`-Header. Details zu Token-Erzeugung, Ablauf und Header-Format findest du unter [Authentifizierung](/authentication).

## Code-First Dokumentation

Die REST-Dokumentation wird nicht separat gepflegt. Server-Dateien registrieren ihre Endpunkte direkt im Code, und die OpenAPI-Spezifikation wird daraus automatisch aufgebaut.

Insgesamt dokumentieren 93 Server-Dateien ihre Routen selbst. Das zugrunde liegende Muster verbindet HTTP-Metadaten mit Zod-Schemas für Request und Response, sodass Validierung und Dokumentation aus derselben Definition entstehen.

```javascript
registerRoute({
  method: "get",
  path: "/api/assets",
  tags: ["Assets"],
  summary: "Listet Assets",
  body: assetsQuerySchema,
  response: assetsListResponseSchema
})
```

Dieses Muster reduziert Abweichungen zwischen Implementierung und Dokumentation. Wenn sich ein Schema ändert, aktualisieren sich Spezifikation und UI auf derselben Grundlage.

## Lokale Spec generieren

Den Markdown-Index der API kannst du lokal aus der registrierten OpenAPI-Beschreibung erzeugen.

```bash
npm run docs:api
```

Der Befehl verwendet das vorhandene Generierungsskript und erstellt den API-Index aus der aktuellen Routenregistrierung. So kannst du Änderungen an Tags, Routen oder Schemas lokal prüfen, bevor du sie veröffentlichst.
