## Überblick

Brainz folgt einer PostgreSQL-first-Architektur. Kritische Geschäftslogik liegt direkt in der Datenbank, einschließlich RLS-Policies, SQL-Funktionen und Triggern für Such- und Integritätslogik. PostGraphile introspektiert das Schema `app_public` und erzeugt daraus die GraphQL-API automatisch, während Multi-Tenancy auf Datenbankebene über Row-Level Security durchgesetzt wird.

<Callout kind="info">

Schemaänderungen propagieren direkt in die API: Wenn sich Tabellen, Views oder Funktionen in `app_public` ändern, ändert sich die von PostGraphile erzeugte GraphQL-Oberfläche automatisch mit. Brainz benötigt dafür keine manuell gepflegten GraphQL-Resolver.

</Callout>

## Design-Prinzipien

### PostgreSQL-First

Brainz legt alle kritischen Regeln so nah wie möglich an die Daten. Dazu gehören SQL-Funktionen mit `SECURITY DEFINER`, Trigger für Suchindex-Updates und Policies für Zugriffskontrolle. Die Datenbank ist damit nicht nur Speicher, sondern der zentrale Ort für Integrität, Autorisierung und Geschäftslogik.

PostGraphile introspektiert das Schema `app_public` und generiert daraus die vollständige GraphQL-CRUD-API. Brainz benötigt dafür keinen separaten Resolver-Layer für Standardoperationen. Die Folge ist bewusst direkt: Schemaänderung bedeutet API-Änderung.

### Multi-Tenancy via RLS

Mandantentrennung wird in Brainz nicht im Anwendungscode nachgebildet, sondern in PostgreSQL erzwungen. Jede relevante Tabelle trägt ein `tenant_id`, und der aktuelle Benutzer- sowie Tenant-Kontext wird über JWT-Claims und `pgSettings` in die Datenbanksitzung übergeben.

RLS-Policies filtern dadurch alle Abfragen automatisch. Zusätzliche Filterlogik im API- oder Service-Layer ist für die Isolation nicht erforderlich. Funktionen wie `current_user_id()` und `current_tenant_id()` liefern den Kontext, auf dessen Basis Policies Entscheidungen treffen.

### Event-Driven

Brainz verwendet PostgreSQL nicht nur als Datenbank, sondern auch als Event-Quelle. Änderungen werden über LISTEN/NOTIFY-Kanäle an die WebSocket-Bridge weitergegeben, damit Clients Realtime-Updates ohne Polling erhalten.

Zeitintensive oder nicht-kritische Arbeit wird in asynchrone Jobs ausgelagert. BullMQ verarbeitet Hintergrundaufgaben wie Content-Enrichment, Embedding-Erzeugung und Benachrichtigungen. Dadurch bleiben API-Antwortzeiten kurz und interaktive Anfragen blockieren nicht auf nachgelagerte Verarbeitung.

### Provider-Agnostic AI

KI-Funktionen sind nicht fest an einen einzelnen Anbieter gekoppelt. Ein AI Service Registry übernimmt das Routing von Aufgaben wie Embeddings, Chat, Vision oder Audio an den jeweils konfigurierten Provider.

Diese Entkopplung erlaubt Providerwechsel ohne Änderungen an aufrufendem Fachcode. Gleichzeitig werden Kosten und Budgets zentral erfasst, sodass Modelle pro Aufgabentyp austauschbar bleiben, ohne die Systemarchitektur zu verändern.

## Datenbank-Architektur

Die Datenbankstruktur trennt öffentliche API-Flächen, interne Systemdaten und temporäre Arbeitsdaten bewusst in verschiedene Schemas. Diese Aufteilung reduziert das Risiko unbeabsichtigter Exponierung und macht klar, welche Teile des Modells in die API eingehen.

### `app_public`

`app_public` bildet die externe API-Oberfläche. PostGraphile introspektiert dieses Schema und erzeugt daraus die GraphQL-Struktur für Tabellen, Relationen und CRUD-Operationen.

Typische Objekte in `app_public` sind `items`, `documents`, `files`, `collections`, `teams`, `tags`, `notifications` und `knowledge_entities`. Alles, was hier sichtbar ist, muss als Teil der öffentlichen Daten- und Berechtigungslogik verstanden werden.

### `app_private`

`app_private` enthält interne Tabellen, die nicht über die API exponiert werden. Dazu gehören sensible oder rein systeminterne Daten wie Passwort-Hashes über `pgcrypto`, interne Tokens und Audit-Daten.

Diese Trennung verhindert, dass sicherheitskritische Strukturen versehentlich Teil der generierten API werden. Gleichzeitig bleibt Authentifizierungs- und Betriebslogik nah an den Daten, ohne die öffentliche Oberfläche zu vergrößern.

### `app_hidden`

`app_hidden` dient als Bereich für Zwischenstände und temporäre Daten. Dazu gehören interne Hilfsstrukturen und Metadaten, die bei Hintergrundverarbeitung oder Übergabeschritten entstehen können.

Das Schema ist ausdrücklich kein Teil der externen API-Oberfläche. Es unterstützt Prozesse, die für den Betrieb notwendig sind, aber keinen stabilen Vertragscharakter gegenüber Clients haben.

### Migrationen und Erweiterungen

Das Schema wird über einen eigenen Migrations-Runner in `scripts/migrate.js` verwaltet. Mehr als 265 Migrationen werden in `public.schema_migrations` nachverfolgt, sodass Datenbankzustand und Deployments reproduzierbar bleiben.

Für semantische Suche und KI-nahe Funktionen verwendet Brainz `pgvector`. Full-Text-Suche basiert auf `tsvector`-Spalten mit GIN-Indizes. Erweiterungen wie `pgvector`, `pgcrypto`, `uuid-ossp` und `pg_cron` werden automatisch installiert, damit die Datenbank alle benötigten Plattformfunktionen direkt bereitstellt.

## Tech-Stack

| Komponente | Technologie | Zweck |
| --- | --- | --- |
| Runtime | Node.js 20+ | Server-Laufzeitumgebung |
| HTTP | Express.js | API-Server, Middleware, REST-Routen |
| GraphQL | PostGraphile | Auto-generierte API aus Schema |
| Auth | Better Auth + JWT + pgcrypto | Authentifizierung und Session-Management |
| Queue | BullMQ + Redis 7 | Hintergrundverarbeitung und Caching |
| Realtime | WebSocket + LISTEN/NOTIFY | Echtzeit-Events an Clients |
| Collaboration | Yjs | CRDT-basierte Dokumentbearbeitung |
| Storage | S3-kompatibel, MinIO oder R2 | Dateien und Medien |
| AI | Multi-Provider, OpenAI, Anthropic, Ollama | KI-Funktionen |
| Edge | Cloudflare Workers | CDN, RSS, E-Mail-Ingestion |
